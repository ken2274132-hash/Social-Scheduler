## ⚠️ Do these two things first

### 1. Run the migration

`supabase/migrations/20260831_harden_token_columns_and_policies.sql` — paste it into
the Supabase SQL editor. It is idempotent.

It revokes column-level `SELECT` on `social_accounts.access_token`,
`social_accounts.refresh_token` and `shopify_accounts.access_token`, so a future
`select('*')` **errors** instead of silently leaking credentials. It also adds the
DELETE policies that were missing on `posts` and `media_assets`, and tightens the
`ai_generations` insert policy.

The application fixes work without it. This is what stops the mistake recurring.

### 2. Rotate the social tokens

Finding C1 was live against the production database. Every connected Facebook Page
token and Pinterest access/refresh token was being serialized into page HTML on
`/settings`, `/composer`, `/workflow` and `/calendar`. Treat them as exposed:
have users disconnect and reconnect their accounts.

## What was fixed

| ID | Issue | Fix |
|----|-------|-----|
| C1 | `select('*')` shipped OAuth tokens to the browser on 4 pages | Explicit column lists via `SOCIAL_ACCOUNT_PUBLIC_COLUMNS` in `lib/api.ts`, plus the column-level `REVOKE` migration |
| C2 | Shopify callback POSTed `client_secret` to any attacker-named `shop` | Domain regex before any fetch, plus Shopify's mandatory HMAC verification |
| C3 | `/api/cron/publish` was fully public | `Authorization: Bearer $CRON_SECRET`, timing-safe compare |
| H1 | `/api/ai/generate` had no auth — anyone could spend the Groq quota | `requireAuth()` + workspace ownership check + input cap |
| H2 | `ignoreBuildErrors` / `ignoreDuringBuilds` hid a real type error | Flags removed; type error fixed; build and lint both clean |
| H3 | Admin authorization used `getSession()` (unverified cookie) | `getUser()` everywhere; role re-checked inside `app/admin/*`; `protectedPaths` extended |
| H4 | OAuth `state` was an unsigned client-controlled blob | `lib/oauth-state.ts` — random nonce in an httpOnly cookie, all three flows |
| H5 | Upstream/SQL error text returned to clients | `errorResponse()` logs detail server-side, returns a generic message |
| B1 | AI captions dead — Groq decommissioned `llama-3.3-70b-versatile` | `openai/gpt-oss-120b` with automatic fallback to two more models |

## Local development without logging in

`lib/auth.ts` provides a bypass so you can work without the login screen:

```bash
# .env.local
DEV_BYPASS_AUTH=true
DEV_BYPASS_USER_ID=<uuid of a real user in public.users>
```

It is gated on `NODE_ENV === 'development' && DEV_BYPASS_AUTH === 'true'`. Vercel
always sets `NODE_ENV=production`, so the flag cannot open up the live site — this
was verified by running a production build with the flag set and confirming
`/dashboard` still redirects and the cron still returns 401.

To build while the dev server is running (they otherwise fight over `.next`):

```bash
NEXT_DIST_DIR=.next-prod npm run build
```

## Still open (from the audit, not yet addressed)

- **No tests, no CI.** `lib/posting-engine.ts` has real third-party side effects and
  zero coverage. B2 is exactly the kind of bug a test would have caught.
- **Tokens are stored in plaintext** (M2). The migration hides them from the client;
  encrypting at rest, or moving to Supabase Vault, is the follow-up.
- **No rate limiting** (M5) on the AI or publish routes.
